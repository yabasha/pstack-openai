### Visual parity

Read the complete [mode](../SKILL.md) and each applied principle leaf before acting. Copy these five steps verbatim into an available todo list or an authorized local checklist with a disclosed reduced binding. Discover [session capabilities](../../../references/host-capabilities.md), follow [model roles](../../../references/model-roles.md) and the [assignment contract](../../../references/orchestration-contract.md). Read the complete [poteto role prompt](../../../references/agent-prompts/poteto-agent.md) before any authorized delegation. Use inherited model and effort unless supported selection is observed. Record requested and actual selections separately.

**You own pixel-exact equivalence. The baseline is the spec. You do not touch it.** Equivalence is verified by image diff, not by eye.

1. Establish the baseline first, before any migration: a visual regression harness that screenshots the current component across its states, plus the target when matching two implementations. Capture actual rendered output on the matching surface through an exposed and authorized control operation. Discover the matching control companion, such as control-ui for browser or web UI, and read its contract when available. Retain the baseline screenshots and harness location. No baseline, no parity claim. This is a blocking prerequisite, not a follow-up. Missing controls or rendering execution block the visual pass; source inspection, fixtures and type checks cannot replace it.
2. Anti-shortcut clauses, stated and held: no harness modifications, no baseline tampering, no component restructuring to make a diff pass. If the baseline looks wrong, stop and ask, do not edit it.
3. Migrate one component at a time. Parallelize across worktrees, one owner per component under the [separate-before-serializing-shared-state](../../principle-separate-before-serializing-shared-state/SKILL.md) principle skill. Shared primitives migrate first as a blocking phase. Assign distinct owned paths and isolated worktrees before authorized worker writes. Observe worker creation and inspect returned artifacts before claiming parallel execution. Without authorized independent workers or isolation, migrate sequentially as reduced capability and disclose the unsatisfied parallel gate. Do not install tools or create an unapproved worktree as a fallback.
4. Verify each component against its baseline via image diff on the matching surface via the control skill. Capture and inspect the actual rendered result across the baseline states and retain screenshots, diff artifacts and the numeric result for each component. A nonzero diff is a fail. Investigate the pixel delta. Repeat the per-component loop until the diff is zero using exposed and authorized execution. The /loop alias is invocation guidance, not proof of a host loop operation. If that companion is absent, disclose it and use an authorized explicit repetition as reduced capability. Missing image-diff execution or matching controls leaves verification blocked. Do not claim parity from visual judgment or a worker report without the artifacts.
5. Run **Opening a PR** per component or per safe batch. Read the complete opening-a-pr playbook at skills/poteto-mode/playbooks/opening-a-pr.md and follow its review, companion, commit and delivery gates when available. This remains a deferred task 21 dependency for task 24 integration until the file exists. Stop PR-dependent work if absent. Commits, push and PR creation require their actual authorization and operations. Otherwise return the checked local diff and delivery plan with those actions unperformed. Opening a PR never starts Babysit implicitly.

**Reply:** components migrated, the diff result for each, the baseline harness location, what is left. Link the actual rendering and diff artifacts. Include missing capabilities, denied permissions, reduced checks and unperformed delivery steps. Structural validation and inert fixtures never establish visual parity or host support.
