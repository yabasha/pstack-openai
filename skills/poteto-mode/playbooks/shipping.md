### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.**

This is the half after [babysit](babysit.md). It owns requests to land or ship. Apply [workflow ownership](../../../references/workflow-ownership.md), [session capabilities](../../../references/host-capabilities.md), [model roles](../../../references/model-roles.md) and the [assignment and action contract](../../../references/orchestration-contract.md).

Record the active forge, repository, exact trunk tip, frozen bottom-to-top PR list and each verifier assignment before action. Check explicit user authorization for merge or merge-when-ready. Posting verdicts, publishing branches and retargeting each require their own authorized scope and available binding. Verification alone authorizes none of them. Prepare local artifacts when writes are denied. After interruption, inspect the prior action identity and destination before replay; an unknown outcome blocks replay.

Use the caller's watch budget or at most 10 snapshot attempts and 600 seconds for this invocation. Carry the remaining budget across re-arms and merges. Stop on user stop, exhausted budget, denied access or unavailable operation, preserving the last observed frontier and unknowns. Use an exposed authorized loop or wake binding when available. Without one, a bounded foreground watch is reduced capability and registers no background continuation. A helper deadline is checked between reads and sleeps; it is not a hard wall-clock bound. Use an observed stop or execution-deadline binding for that guarantee, or disclose the limitation.

1. **Resolve the forge, then verify every PR independently.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR view, watch, edit, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One subagent per PR, not batched, each an independently spawned worker through an observed host binding, each exercising the real surface with the matching exposed and authorized control skill against exact parent versus head revisions. The upstream examples `control-ui` and `control-cli` are external skills, not bundled bindings. Missing control capability leaves real-surface verification blocked. Use inherited model roles unless current supported selection and actual results are observed. Each returns `PASS`, `PASS+NOTES` or `FAIL`, with verifier identity, exact revisions and method artifacts, and posts that verdict on its own PR when comment authorization exists. Otherwise retain the verdict locally and report that posting is blocked. A missing worker permits local sequential recommendations as reduced capability, never an independent verdict or a landable run. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable. An independent PR whose branch neither holds nor needs the lower code may move onto trunk only within authorization and with a fresh independent verdict, since its prior verdict included code trunk lacks. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without touching a check. Before landing a PR, read and record its current exact head SHA and base SHA, resolve the base-to-head diff at those revisions, and compare the recorded patch-id with its current base-to-head patch-id. Re-read the head and base immediately before the authorized merge or arm action. If either moved since the freshness check, stop and repeat that check. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. Re-verify anything else when the patch changed. When it did not, keep the code verdict but re-run mergeability and CI at the current head. Never use matching commit messages or a green check from an older SHA as a substitute.
4. **Prepare only the bottom PR.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push it, and retarget only that PR to trunk through an exposed built-in PR tool when present, as required by [opening a PR](opening-a-pr.md). Without that tool use `origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`. Re-run step 3 after the push. Do not retarget, arm, or merge descendants yet.
5. **Land one PR at a time.** If the bottom PR is mergeable now, use the resolved forge's observed merge contract, such as `origin pr merge <pr>` or `gh pr merge <pr> --squash`. Origin's plain command can include lower PRs, so name only the verified lowest unmerged PR. A GitHub PR still based on its parent merges into that parent, so confirm its base is trunk before action. If requirements are still running and the user asked for merge-when-ready, arm only that PR with `origin pr merge <pr> --squash --auto` or `gh pr merge <pr> --squash --auto`. Origin's `--auto` is Origin merge-when-ready. GitHub's `--auto` is GitHub auto-merge. Read the PR back through the resolved forge after the action. A command reporting success may have only queued it. Confirm merged state, merged revision and trunk base before claiming landing. Wait for that PR to merge before preparing the next one.
6. **Do not read GitHub `autoMergeRequest` as stack readiness.** At most it says GitHub auto-merge was requested for one GitHub PR. It does not prove Origin merge-when-ready is armed, that a descendant is queued, that a patch verdict is current, or that the contiguous stack is safe. Confirm the active forge's state for the current bottom PR, and say that the state is unknown if the active forge cannot report it.
7. **Recompute after every merge.** Fetch trunk, confirm the merged SHA is present, drop the merged PR from the frozen bottom-to-top list, and inspect the new bottom PR's base, head, checks, and patch-id. A host may retarget a child automatically, but do not assume it did. Once the parent is observed merged into trunk, move only its immediate child patch onto the merge result and retarget that child to trunk through the built-in PR tool when exposed. Coordinate exclusive branch ownership, inspect the expected remote SHA and use an explicit pinned force-with-lease for an authorized push. Read back the resulting head and base, apply step 3 and wait for current-head checks. This post-merge movement is the only permitted chain mutation while landing proceeds. Repeat steps 3 through 6 for that one PR. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** With Origin, use `origin pr view <pr> --checks --comments` and `origin pr checks <pr> --watch`, then re-read the PR until it reports merged or blocked. With GitHub, use the read-only [watcher](../scripts/watch-pr/watch-pr) from the package root as `bun --no-install skills/poteto-mode/scripts/watch-pr/watch-pr --owner <owner> --repo <repo> --queued-stack --stack-prs <bottom> --head <bottom=full-40-character-head> --max-polls <remaining-count> --timeout <remaining-seconds>` only as an event wake and poll `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest` after each wake, ignoring `READY` until `mergedAt` is non-null or `state` is `MERGED`. Only then run step 7. Hard-fail only when `state` is `CLOSED` with no `mergedAt`, a required check concludes `FAILURE` or `CANCELLED` and blocks merge after auto-merge is no longer pending, or `mergeStateStatus` is `UNSTABLE` or `DIRTY` with no auto-merge pending. `BLOCKED` while checks are pending or auto-merge is armed is not failure. Do not use Babysit's queued `WAITING`/`merge-queue` stop condition here. Hold the watch through the observed authorized loop or wake binding within the declared budget. Do not add a second sleep loop. The watcher emits NDJSON schemaVersion 1 events. Inspect kind, terminal and reason, never exit 0 alone. Queued mode emits non-terminal `WAITING` with `reason.kind` equal to `merge-queue`, not `READY`. Terminal helper blockers or budget exhaustion require inspection of the active forge, not an invented merged or hard-failed state. The [bootstrap](../scripts/bootstrap.ts) checks pinned dependencies and fails setup-required; never install or bypass it. [Helper setup](../../../docs/testing/helper-setup.md) is separately authorized. For Origin, use a finite bound and an observed stop binding for check watching, or bounded view snapshots when an unbounded watch cannot be stopped. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
